**What makes this board different from the fleet's:** every other board in this corpus scores an *unbuilt* concept against Build/Adopt/Defend gates. The Value Ledger is not unbuilt — `tasks.md` shows **55/55 tasks checked** `[CS: VERIFIED — grepped this pass: 55 lines matching \`- [X]\`, 0 matching \`- [ ]\`]`, and the code exists (`apps/backend/app/value_ledger/{models,service,rollup,baseline_resolver,schemas,seed_defaults}.py`, a migration, and Temporal export/reconciliation workflows wired into `runs/temporal/worker.py`). So the required positions here are not "will this get built" — they're **post-build survival gates**: does the built thing produce real data, get trusted, survive scrutiny, and reach an audience. That reframing is itself the finding.

## Required positions

| Position | [A] P | Reasoning |
|---|---|---|
| **Produce** — a real upstream producer (execution engine + Coworker/Expert runtime) calls the ledger with real completion data, not $0 | 0.25 | The spec's own Dependencies section flags both integrations this depends on as *"(High risk.)"* — twice, back to back: "**Execution engine** — must emit a completion event with task category, action type, actual duration, and Coworker/runbook identifiers. Required for all ledger writes. *(High risk.)*" (spec.md:256) and "**AI Coworker / Expert runtime** — must report `estimated_human_minutes` for `ai_reasoning` runs. Required for AI reasoning value tracking. *(High risk.)*" (spec.md:257). Grepping this pass confirms the risk is live, not theoretical: `write_entry`/`WriteEntryRequest` are called only inside `value_ledger/service.py`, `value_ledger/schemas.py`, the ledger's own `reconciliation_activity.py`, and the API router `api/v1/value_ledger.py` — **zero call sites in `app/runs` or `app/agents`**. Nothing in the execution/runtime layer currently emits an entry. This is Death Pattern #6 verbatim: *"the ledger renders $0 (no producer)"* (fleet synthesis §1.6) — and it is this exact artifact the fleet synthesis was describing. |
| **Trust** — the self-reported `ai_reasoning` baseline is accepted as credible by the MSP reading it | 0.35 | FR-003 has the Coworker report its own `estimated_human_minutes` as the baseline for the harder-to-verify half of the ledger's value story — the system estimating the value of its own work (spec.md:147, `baseline_source: coworker_reported`). Guardrails exist but are edge-only: a zero estimate is rejected (spec.md:131), and >8h is "flagged for review" but *"the run is not blocked"* (spec.md:136) — neither catches a plausible-but-inflated number. The spec itself treats this as unresolved, not solved: **SC-007** — *"MSPs report confidence in the value numbers in the first user research round — the majority response is 'I trust these numbers' (qualitative measure)"* (spec.md:226) — is a success criterion phrased as a hypothesis to be tested, with no research round scoped elsewhere in this document. This is Death Pattern #2, *"the operator was never studied"* — here, the operator's trust in a self-graded number was never studied. |
| **Defend** — exported, client-facing numbers survive scrutiny without a defensibility-tiering mechanism | 0.40 | User Story 3's acceptance criteria promise a PDF *"showing aggregate value, Coworker breakdown, methodology notes, and branding — suitable to hand to a client"* (spec.md:91) — i.e., this ledger's numbers are explicitly designed to leave the platform and sit in front of a client, the exact position where the fleet synthesis's death pattern #5 lives: *"the narrative layers have no defensibility tiering"* (fleet synthesis §1.5). The only provenance signal this spec defines is `baseline_source` (tenant_configured / platform_default / coworker_reported, FR-011, spec.md:158) — which names *where* a number came from, not *how confident* it is. No Measured/Benchmarked/Estimated/Unverified-style tiering exists anywhere in this document. "Methodology notes" is a paragraph, not a machine-checked confidence level. |
| **Capture** — the ledger has a real downstream consumer, so its numbers reach anyone | 0.30 | Out of Scope explicitly closes off the one path that would force this: *"Financial billing or invoicing based on value (the Ledger tracks value, not charges)"* (spec.md:248) — this artifact deliberately has no direct monetization hook. Its only route to mattering is as plumbing under a client-facing offering, exactly as the fleet synthesis frames it: *"wire it to the Value Ledger (built) so ROI renders non-zero"* (fleet synthesis §4, step 3) as a precondition for Package A/3. That consuming runbook is, per the fleet synthesis, itself still gated on Q1/Q2 and two unresolved P0 studies as of 2026-07-14 — nothing in this repo shows that gate cleared. A fully-built, fully-tested ledger with no runbook writing to it is Death Pattern #6 from a second angle: substrate with no demanded thing sitting on top of it. |
| **Adopt** — MSP Admins actually configure custom baselines at the rate the spec bets on | 0.35 | **SC-006**: *"More than 40% of tenants configure at least one custom baseline within 30 days of launch (adoption signal that the customization flow is discoverable and usable)"* (spec.md:225) is a specific, falsifiable behavioral bet with no operator study behind it in this document — no Q2-style mechanism test, no usability pass cited. FR-011's "using default" indicator + customization prompt (spec.md:158) is a reasonable UX nudge but is unproven UI, not tested UI. Same root pattern as **Trust**: Death Pattern #2, operator behavior assumed rather than studied. |

**Naive survival:** 0.25 × 0.35 × 0.40 × 0.30 × 0.35 = **~0.37%**.

**Dies first at:** **Produce** (0.25) — the lowest position, and the only one backed by the spec's own authors naming it "High risk" twice rather than an outside estimate.

**Correlation flag:** **Produce** and **Capture** are not independent — both are downstream of the same single root question: *does a real consuming runbook exist that both emits completion events into this ledger and reads them back out into a client-facing artifact?* If no such runbook exists, Produce never fires (there's nothing to tag as a value-tracked run) and Capture fails by the same stroke (there's no audience for the numbers regardless). Treat 0.37% as a ceiling, not a floor — the true number, once this correlation is priced in, is closer to a single ~0.25–0.30 gate than a chain of five. Separately, **Trust** and **Defend** are two faces of one question asked at different layers — "is this number's provenance strong enough to survive scrutiny," asked once at the raw-entry level (self-reported estimate) and once at the exported-report level (no tiering) — so their joint 0.14 is also likely overstated by treating them as independent.

**Single test that would move the floor most:** wire **one** already-seeded task category (e.g. `patch_deployment`, present in `seed_defaults.py`) from a real running Coworker so it actually calls `POST /entries` on live tenant data for a week. This is the cheapest available test that hits the lowest position (**Produce**) directly, and it's the only test on this board that simultaneously de-risks **Capture** (proves a real consumer can attach) — it converts the artifact from "55/55 tasks complete, zero real entries" into a live data source, which is the precondition for testing **Trust**, **Defend**, and **Adopt** with real numbers instead of speculation. This mirrors the fleet synthesis's own stated next step for the ledger almost exactly (fleet synthesis §4, step 3).
