## Service Blueprint (§4) — An existing artifact shape exists; it is not designed for what this log needs to do

- **New finding:** N-central's Incident Summary Report structure — Summary Information (incident counts, escalation/acknowledgment times), Detailed Incident Data (affected devices, service states, timings), Correlated Notifications — is a real, shipping precedent for structured incident-level reporting [CS: VERIFIED — scout_input/09-ncentral-incident-reporting.md lines 9-26]. Critically, it reports on incidents that occurred and escalated — not on suppressions that never surfaced. "Report provides data for analysis but does not trigger automated remediation" [CS: VERIFIED — line 40].
- **Touches:** Original Hypothesis — "A stream of hundreds of suppressions nobody has time to review is not a reviewable log — it is a liability disclosure" (line 82). Also touches the Cannot-see about support/maintenance processes for suppression-rule drift (lines 90-91).
- **Update type:** net-new-but-minor / contradicts-by-omission. The existing report format is the closest artifact precedent N-able has, but it is built for the opposite direction of visibility (surfacing what happened, not surfacing what was silently dropped). It does not answer the objection; if anything it demonstrates N-able has not yet built the "exception-surfacing" artifact this voice calls for.
- **Also relevant:** the generic "audit trail — every action logged with timestamp" trust-score component [CS: VERIFIED — scout_input/01-control-plane.md line 37] confirms logging is architecturally expected department-wide, but says nothing about scannability, sampling, or exception-surfacing design — the objection in the original ("Dumping 400 rows is not design") is untouched.

- **New finding:** The department's 5-layer monetization stack names Layer 3, "Expert Licensing," as the layer "where trust-level becomes monetizable — MSPs pay recurring fees for each Expert, and trust level determines how much labor each Expert replaces" [CS: VERIFIED — scout_input/01-control-plane.md lines 39-47]. Separately, both TAM-grounding docs confirm no public ACP per-tech price exists: "[A3] Agent-seat ARPU... NEW category, no price precedent. MOST FRAGILE" [CS: UNKNOWN — scout_input/acp-tam-control-plane.md line 57] and "No public ACP per-tech price exists. The $/tech/mo... is a LOAD-BEARING ASSUMPTION" [CS: UNKNOWN — scout_input/acp-tam-grounding.md line 9].
- **Touches:** Original Kill criterion — "the value chain says: own the chokepoint... but find the margin layer *above* the chokepoint" (line 106); original Cannot-see (line 112, whether MSP margin increases when the agent handles suppression, unknown).
- **Update type:** strengthens + complicates. It strengthens the original's framing that the margin lives above the raw data/chokepoint — Expert Licensing is explicitly that layer. It complicates the binary the original section poses ("free-in-RMM platform feature" vs. "priced as coworker") by naming a third path already architected at department level: bundle base suppression into Platform Access (subscription, effectively "free"), meter/price advanced trust-graduated behavior through Expert Licensing. Nothing in the new research confirms Alert Flood Suppression specifically will use this path — this is architecture, not agent-specific decision.
- **Secondary, minor:** Per-tech ARPU precedent exists in adjacent tooling — Atera ~$129-219/tech/mo, NinjaOne ~$1.50-3.75/device/mo [CS: HIGH/MEDIUM — vendor list prices, scout_input/acp-tam-control-plane.md lines 42-46] — single-vendor anchors [WOBBLY], not alert-suppression-specific, but a real starting point for the pricing test Lean Startup says doesn't exist yet.
