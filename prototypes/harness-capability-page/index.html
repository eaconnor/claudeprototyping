Roadmap — not shipped, not scheduled here
Planned

Eleven capabilities that are specced and not built

These are held in one card, at one weight, on purpose. Given a card each they would read as a product line. Each of the eleven has a written spec and no working build. No date is attached to any of them on this page.

  • Risk-based work prioritization — ranks work by risk. It does not route tickets to technicians, and models no technician skill, availability or workload.
  • Real-time vulnerability assessment
  • Context-aware troubleshooting and root-cause analysis
  • Asset insights and auto-recommendations
  • Endpoint health and lifecycle analysis
  • Documentation and knowledge-base assistant — a standalone coworker, not an input to a resolution loop.
  • Licence and cost optimization
  • Fast asset and user lookup
  • Scheduling and notifications — cron scheduling, in-app and email notification, quiet hours.
  • Self-serve onboarding to first value with no prerequisite N-able product
  • Operator model — the control plane itself operable by an MCP client

Two rows here attract a claim they cannot support, so read them literally.
Risk-based work prioritization is not ticket dispatch. It orders work by risk. It is a different object from routing a ticket to a person, nothing in our sources models technician skill, availability or workload, and the one shipped piece of work with “dispatch” in its name dispatches coworker runs, not tickets to humans — it does not back this row.
Scheduling is on this list, not on the shelf above it. Runs today are triggered on demand only. Scheduling cannot be claimed.

Where these 16 cards come from, and what is deliberately not here

  • Every card traces to a named row in crosswalk/neoagent-harness-capability-crosswalk-2026-09-04.md, which states of itself that nothing in it is a decision. No row was added, invented, or promoted to a higher state.
  • Counted from that source: 8 built · 7 in development · 11 planned in this track. The 11 planned rows are consolidated into a single card rather than shown as eleven.
  • Marker definitions were chosen by this build against evidence of a build, because the operative meaning of “Available” to this page’s reader is unresolved. That definition is not signed.
  • Sourcing is strong but narrow — nearly all of it traces back to one crosswalk document. Treat the single-source concentration as a condition on every state shown.
  • Type and shape follow the Apex 2.0 pull: Manrope headings, Inter body, radius 2/4/8/16/999, soft shadows. No monospace face — none exists in the 2.0 file and the older generation’s mono tokens are not borrowed. Light only — the 2.0 pull has no dark-mode values and this build does not invent them.
