## 💰 A note on GA Billing (the constraint that overrides Sources 01–02)
- BizApps **won't** have systems to offer a fully self-serve option where users select from three credit plans for GA.
- If an org runs out of monthly credits, they **must contact Sales** to purchase more.
- Sales (via Salesforce) notifies PMs to change the org's plan **manually**.

### UX implications
- UI displays the plan but does **not** allow plan changes on AI Settings. User is told they can only change plan by contacting Sales.
- When limits approach/reach, messaging changes to indicate "change your plan via Contact Sales."
- Documentation updated to reflect this model; UI links to docs.
- Add starter prompt: "How much does N-zo cost?"

### Key characteristics of GA (from BizApps)
- Customers receive an included **100 credit** allocation.
- When more credits needed, customers are prompted to contact Sales.
- Additional credits quoted, contracted, billed via existing As-Is quoting/billing model.
- Quote uses predefined packages (currently discussed as **250-credit** and **500-credit** options).
- Once purchased, available credit limit increases accordingly.
- N-zo continues to report consumption and notify as customers approach limits.
- When purchased limit is reached, usage stops until more purchased or reset next period.
- Rationale: predictable, controlled spend; launch on existing operational processes.

## The divergence (carry, do not resolve)
Source 01 requirements and Source 02 study both assume **self-serve** upgrade. Source 03 GA reality is **Sales-mediated, manual, no self-serve**. The dashboard is therefore *decision support that routes to a human*, not a transaction surface — for GA. Self-serve remains a post-GA question the study was designed to answer.
