Technical Overview
The N-able control plane is the governing layer for AI Agents operating within the N-able
product ecosystem. It serves three distinct but related functions: it is a full orchestration layer
for N-able's own first-party AI agents (AI Experts), managing their execution path, resource
allocation, and runtime policy; and it is a management plane for vendor-supplied agents and
skills, governing their lifecycle, certification, and the conditions under which they operate within
a customer environment and for Customer created AI Agents called AI Coworkers.

AI Agent is the fundamental unit of the ecosystem. An agent combines an identity, a runbook, a
set of tool access permissions, and a designated LLM into a deployable entity. Each deployed
agent instance receives its own scoped identity there is no shared service principal across
customers or deployments. This means two customers running the same Agent Expert are
operating distinct principals with independent permission scopes.
Agent identity is modelled on the concept of an office worker with a defined role and access
rights. Each deployment gets an identity that expresses what the agent is permitted to do,
which systems it can reach, and under what conditions. Identity is enforced at runtime, not at
configuration time.

MCP servers (and CLI and APIs and whatever mechanism comes next) are the mechanism
by which agents access software systems. They form the tool access layer sitting between an
agent and the services it needs to operate. Which MCP servers an agent may use, and with
what scope, is governed by the control plane (particularly for vendor agents, where permitted
servers and scopes are explicitly bounded).
MCP keys and credentials are managed by a dedicated key service, separate from the
control plane itself. The key service is responsible for credential vaulting and issuance, and
issues credentials scoped to a specific deployment rather than to an agent type. This means
credential rotation and revocation operate at the deployment level.
LLMs are always external. N-able does not build or operate its own models. Customers may use
N-able's processing infrastructure (which routes to a supported external model) or bring their
own model and API key (BYOK/BYOM). In the bring-your-own case, the control plane hands off
to the customer's chosen model and does not sit in the inference path. LLM selection is a per-
agent configuration.
The script repository provides deterministic, non-AI tooling that agents can invoke for activities
where predictable, auditable execution is required. This is distinct from MCP-based access and
represents a lower-variance execution path for well-defined operations.
Runbooks describe what an agent will do (can be as simple as a prompt or as complex as
multiple SOPs). Runbooks can be authored by N-able, by vendor partners, or by customers
directly. They can be uploaded or generated. The control plane does not pre-screen or approve
runbooks before use. This places responsibility on the runtime layer to catch out-of-policy
behavior regardless of runbook provenance. This is a big ‘unknownʼ. Runbooks may be as
simple as a prompt, or as complex as containing multiple workflows.

Agent types
AI Agent Experts are fully preconfigured AI agents released by N-able. They carry a complete
end-to-end use case, a fixed runbook, defined tool access, and an N-able-managed identity.
They require no customer configuration to deploy and operate entirely within the orchestration
layer.
Approved Vendor Experts are AI agents built by third-party vendor partners and certified by N-
able for use within the ecosystem. Certification involves N-able reviewing the agent's intended
behavior, permitted MCP scopes, and compatibility with ecosystem policy. Once certified, a
Vendor Expert is listed in the agent catalogue and available to customers. Vendor Experts are
managed through the management plane rather than the orchestration layer. N-able governs
their lifecycle, versioning, and policy compliance, but does not necessarily own their runtime.
Control plane responsibilities
Orchestration layer (first-party agents)
For Agent Experts and Coworkers executing on N-able infrastructure, the control plane owns the
full execution path. Its responsibilities include:
Routing agent requests to the appropriate LLM endpoint, whether N-able-hosted or handed
off to a customer-supplied model
Enforcing agent identity and permission boundaries at runtime
Brokering MCP server access by requesting appropriately scoped credentials 
Applying runtime policy against agent actions If it owns the runbook provenance
Providing execution context and resource management for the agent's lifecycle
Management plane (vendor agents)
For Approved Vendor Experts, the control plane acts as a governance and certification authority
rather than a runtime executor. Its responsibilities include:
Operating the agent catalogue: onboarding, versioning, and certification of vendor agents
Allowing the vendor to define permitted MCP server access and credential scopes for each
vendor agent
AI Coworkers are user-assembled super-agents. A customer builds a Coworker by combining
their own runbooks, their own MCP configurations, and any mix of Agent Experts and Approved
Vendor Experts. The result is a custom workflow tailored to the customer's environment.
Coworkers execute within the orchestration layer, but the vendor agents they embed may
execute either on N-able infrastructure or on the vendor's own infrastructure, at the customer's
discretion.

Customization: When Defaults Are Not Enough
Eventually, the MSP wants to customize. Their biggest customer has a specific onboarding
policy. Their vertical requires a particular compliance report. They want alerts from a third-party
tool correlated alongside N-able alerts.
They open the Coworker Builder in the ACP. They clone the default Onboarding Coworker. They
modify the runbook to add the custom steps. They add a Vendor Expert from the marketplace
(the Halo Ticket Expert, the SentinelOne Expert, whatever they need). They test it in sandbox
mode. They publish it.
At no point do they open UEM, Cove, or Adlumin to make this customization. The ACP is the
authoring environment. The products are the execution infrastructure.
If they write a custom script for a specific remediation, they write it in the ACP's script
repository. It becomes available to any Coworker. If they build a custom runbook for a niche use
case, it lives in the ACP and any Coworker can reference it.

The job of monitoring is to capture every agent action, every tool call, every credential issuance,
and every customer outcome, categorize it, and make it usable for three distinct audiences:
operations (is it working), finance (what do we charge), and compliance (can we prove what
happened).

Use Cases: Example with us and a Halo Expert 
A managed service provider (MSP) uses Halo as their ticketing system. When a new employee
joins one of their customers, someone raises a ticket in Halo to kick off the onboarding process.
The MSP has built an Onboarding AI Coworker in N-able. They wrote a runbook for it that says:
when an onboarding ticket comes in, provision an identity for the new user and allocate them an
asset. They've embedded the N-able Identity Expert and Asset Expert into the Coworker to
handle those two jobs.
Here's what happens end to end:
Halo's Ticket Expert — a vendor agent certified in the N-able ecosystem ingests the ticket and
passes it to the control plane. The management plane validates the payload and checks it

--- PAGE 18 ---
against policy before anything proceeds.
The control plane then triggers the Onboarding Coworker. It reads its runbook, sees it needs to
do two things, and delegates to the Identity Expert and Asset Expert in parallel. Before either
Expert does anything, the orchestration layer issues each one its own scoped identity and
fetches the right MCP credentials from the key service. 
The Identity Expert provisions the new user's identity in N-able. The Asset Expert allocates a
device or asset to them. 
When both complete, the Coworker collects the results and confirms the runbook is satisfied.
The full execution trace is written to audit.
Finally, the result is passed back to the Halo Ticket Expert, which updates the ticket to show
onboarding is complete.

Network Incident Resolution: Deterministic + Non-Deterministic in Action
A network error fires. The N-able Monitor Expert catches it and triggers the customer's AI
Coworker, which orchestrates the entire response (it has their SOPs and connections to their
favored network vendor).

--- PAGE 31 ---
The Coworker calls the Vendor Network Expert, a third-party agent that pulls device state,
topology, and error logs. That data flows to the N-able Vulnerability Expert, which analyzes it
against known CVEs and determines a specific remediation: patch a firewall rule on Device X.
The Coworker then consults the N-able Script Expert, which searches the Script Repository
and finds a validated script that performs exactly this action via direct API calls. The Script
Expert flags it as deterministic, meaning no model reasoning is required to execute it.
The Coworker hits a decision gate: "Can this action be completed without a model?" The
answer is yes. So instead of having the LLM generate API calls (burning tokens and risking
hallucinated parameters), the Coworker hands off execution to the Script Execution Engine,
which runs the script directly. The agent process pauses. The script runs, the result comes
back, and the Coworker logs the outcome.
Five agents collaborated using model reasoning to diagnose the problem and identify the fix. But
the moment the action could be performed deterministically, the system stopped spending
tokens and handed off to validated, auditable code.
