Council Testimony — LOTL Detection
Executive Summary: Readiness score 18/30 (concept stage). Council identified 7 major tensions across frameworks. Core insight: LOTL detection is not a feature—it's a capability that challenges MSP business models (manual SOC) and user mental models (trust in "legitimate" tools). Highest risk: alert fatigue erodes trust faster than accuracy builds it.
Fast Mode: 7 key tensions for decision-making · ~2 min read
1. Jobs-to-Be-Done: Capability seeking a job
▼
Tension: Adlumin has the technical capability (PowerShell ensemble model) but no validated job-to-be-done. What job is the MSP hiring LOTL detection to do? "Detect threats" is not a job—it's an output. Is the job "sleep at night knowing sophisticated attacks won't hide in admin noise"? Or "prove to clients we catch what competitors miss"? Or "reduce time spent chasing false positives in PowerShell alerts"?

Implication: If the job is undefined, marketing will position against imagined pain. Sales will demo features customers didn't ask for. The capability will exist but not sell.
2. Service Blueprint: Human handoff gap
▼
Tension: LOTL detection generates high-confidence alerts, but then what? Prototype shows "isolate workstation, contact user, decode command"—all manual steps. If Northwind MSP's SOC is already underwater (11K alerts/day, 44% uninvestigated), adding more high-quality alerts without backstage orchestration just moves the bottleneck.

Implication: LOTL detection must ship with automated triage (RACE) or it becomes a cognitive load problem, not a solution. Service blueprint shows the alert is frontstage; the isolation/response workflow is backstage and currently manual.
3. Self-Determination Theory: Competence vs. autonomy
▼
Tension: Explainability panel surfaces competence ("I understand why this was flagged"). But high-confidence alerts constrain autonomy ("AI says Critical—are you really going to ignore it?"). SDT predicts analysts will resist if they feel the system is overriding their judgment, even when the system is correct.

Implication: UI must preserve analyst agency. "Suggested action" must feel like a recommendation, not a directive. Override mechanism must be low-friction and not shame the analyst. This is a trust design problem, not just an accuracy problem.
4. Disruptive Innovation: LOTL detection challenges MSP labor model
▼
Tension: Manual MSP SOCs (Arctic Wolf, ConnectWise) sell labor-hours. Automated LOTL detection reduces the need for human triage—good for customers, threatening to labor-based competitors. If Adlumin's positioning is "AI does what manual SOCs miss," it's disruptive. But that requires Adlumin to win on outcomes (attacks caught, time saved), not features (PowerShell model exists).

Implication: Competitive framing must be outcome-based. Don't say "we detect LOTL." Say "we catch the attacks that hide in your admin tools—automatically." This is a business model disruption, not a feature add.
5. Value Chain: Detection without response is incomplete value
▼
Tension: LOTL detection is inbound logistics (threat data) + operations (AI model) + outbound logistics (alert). But the value chain doesn't end at the alert. Customer value is realized in service (response, remediation) and after-sales (learning, tuning). If Adlumin stops at the alert, MSPs bear the response cost. If competitors include MDR, they capture more value chain.

Implication: LOTL detection must integrate with response workflow (RACE, playbooks, isolation) or it's an incomplete value prop. Alternatively, position as "detection for MSPs who do their own response"—but then value is constrained by MSP capability.
6. Language Gap: Vendor term vs. practitioner problem description
▼
Tension: Web research confirms vendors say "LOTL," practitioners say "can't tell legitimate from malicious" or "looks like admin work." Prototype bridges this with translation labels ("looks like admin work—but suspicious"). But if sales decks use "LOTL" and customers don't recognize their own problem in that framing, positioning fails.

Implication: Marketing must use dual framing: "LOTL" for industry credibility, practitioner language for resonance. Sales training must teach reps to ask "how do you currently distinguish legitimate PowerShell from malicious?" and listen for the pain, not the buzzword.
7. Alert Fatigue: Accuracy alone doesn't solve trust erosion
▼
Tension: Brief's counter-metric is correct: "If LOTL detection is noisy, customers will disable it." But web research shows alert fatigue is already endemic (11K/day, 81% noise, 44% uninvestigated). Even high-confidence LOTL alerts enter a system where analysts are burned out and skeptical. Accuracy is necessary but not sufficient.

Implication: LOTL detection must ship with alert suppression, auto-triage, and feedback loops. If analysts can't easily mark false positives and see the system learn, trust erodes. This is an operational design problem: how does the system get better over time in each MSP's unique environment?
