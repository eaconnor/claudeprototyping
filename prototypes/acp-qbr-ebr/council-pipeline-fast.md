### 1. [EVID — Owen RELATN, #30] ↔ [SIGN — Mode 4 Hypothesis, #05]

The rail's math block (`index.html` lines 344-355) presents a single crisp headline — **43% WORLD-CLAIMS [A]/[?]** — with a footnote naming a self-correction ("originally miscounted this as 56%... corrected 2026-07-28"). Mode 4 Hypothesis reads this as a well-formed, falsifiable-looking artifact: a number, a threshold (30%), a pass/fail state, a visible correction trail. RELATN reads underneath it: the brief's own Gate 2 tally — the gate assessing whether this is "the right thing" — is 67% [A]/[?] (`qbr-ebr-prototype.brief.md` line 125), the single worst gate in the document, and it is not the number the screen surfaces. The screen headlines the blended, better-looking figure; the worst gate stays in the brief, unshown. A viewer reading only the rail sees rigor (self-correction, named threshold); a viewer reading the brief sees that the riskiest gate is worse than the headline implies.

### 2. [FEAT — Owen Design Factor, #03] ↔ [JRNY — Signal Entropy, #26]

*Found by inspecting the actual built table, not restated from the brief.* The risk register (`index.html` lines 247-284) renders six columns: Threat/Risk, Risk Level, Existing Controls, Treatment Plan, Owner, Confidence. For three of four rows, Risk Level and Confidence carry an identical tier-badge value (MEASURED/MEASURED; BENCHMARKED/BENCHMARKED; ESTIMATED/ESTIMATED) — the same information rendered twice in two named columns. Design Factor asks whether this is a modeling error (are Risk Level and Confidence secretly the same variable, in which case one column is redundant) or a genuine two-factor model that happens to correlate in this seed data (in which case the redundancy is coincidental, not structural). Signal Entropy asks the display question regardless of the modeling answer: six columns compete for attention at a glance, and two of them currently carry zero incremental bits per row — the entropy budget is being spent on a repeat, not on the columns that actually differ (Controls, Treatment, Owner). The fourth row breaks the pattern entirely (Confidence shows a lock icon, not a tier badge), which is itself evidence the two columns aren't reliably parallel. Neither voice resolves whether this is a real two-factor model rendered redundantly by accident, or one factor rendered twice on purpose for legibility — the build doesn't say which.

### 3. [LAND — Wardley Mapping, #35] ↔ [FEAT — Kano, #13]

The confirm-gate modal (`index.html` lines 485-502) reuses the Defensibility-tier vocabulary (Measured/Benchmarked/Estimated/Unverified) that the Eng routed card names as "already built" over the `baseline_source` field in the Value Ledger (line 466-469). Wardley reads this as correct evolutionary placement: don't rebuild Product-stage plumbing, wire into what exists. Kano reads the same reuse from the viewer's seat: this vocabulary has never been shown to an actual MSP — Q2 (does the operator want this mechanism at all) is explicitly unresolved in both the brief (Gate 2, line 117-121) and the context.md (§4, "every demand signal in the corpus so far is buyer purchase-intent"). Reuse-for-engineering-efficiency is not the same claim as reuse-being-legible-on-first-contact; a lock icon and a hard-blocked export button, dressed in unfamiliar tier language, could register to a first-time viewer as compliance friction (a Must-Be threat) rather than the Performance delighter the rail's "what you nailed" list treats it as (line 365-367, "Must 8... explicit and enforced").

### 4. [CHTR — Owen Force Levels, #10] ↔ [META — Owen Two-Step Development, #42]

The rail states plainly: "Not ready per the 30% rule — named, not buried" (line 329) and routes a Product card asking to "Confirm which ACP altitude (Candidate 1/2/3) this offering builds toward before scoping past Tier 1" (line 419-420). Force Levels asks what force level the confirm-gate mechanism itself carries: the screen renders it as a hard Must (disabled export button, no dismiss path, modal with no close-and-continue) while the strategic question it sits inside — which altitude, whether this feature shape survives Candidate 2's own named commoditization risk — is explicitly unranked. A Must-level, no-escape UI mechanism is built on top of a still-open strategic call. Two-Step Development reads the identical fact as correct sequencing: a step-1 divergent prototype is supposed to build a concrete mechanism precisely so the org has something real to react to before the altitude decision locks — that is what "Tier 1 · Concept" is for. Same fact, opposite verdict on whether it's premature to have built this hard a gate before the softer, prior question is settled.

### 5. [ECON — Economic Buyer, #29] ↔ [JOBS — JTBD Emotional/Social, #22]

Every ROI line in the rail's four routed cards (lines 417-479) frames value in one of two registers: organizational ("Avoids sunk design/eng cost," line 424) or operator-personal ("Operator trusts what ships... without re-checking it," line 441-442; "Operator gets a tool that matches how they actually want to work," line 457-458). The economic buyer — the MSP owner/partner who actually pays for Layer-3-adjacent capability, named "Craig" in the corpus but unverified (`qbr-ebr.context.md` line 55) — appears nowhere in the screen's ROI framing at all. Economic Buyer names this as a straightforward absence: the artifact's value story has no buyer-facing line. JTBD-Social reads the same gap differently: the confirm-gate's clearest value — defensibility, protecting the MSP if a client or an incident pushes back (Gate 1's own framing, `qbr-ebr-prototype.brief.md` line 5) — is *inherently* a buyer-relevant social job (who has to defend this decision if it's ever questioned), even though the screen frames every benefit in operator-competence terms. One voice says the buyer is missing; the other says the buyer's actual job is present but mislabeled as the operator's.

### 6. [CNPT — Kumar Mode 5 Concept Generation, #36] ↔ [RLZE — Kumar Mode 7 Realize, #39]

The build codes exactly one gate interaction shape with exactly two resolution branches: `resolveGate('remove')` and `resolveGate('rewrite')` (lines 584-596) — remove the claim, or rewrite it as Estimated with a caveat. Concept Generation reads this as thin: no alternative gate shapes are visible anywhere in the build (soft-defer-to-next-review, escalate-to-a-named-reviewer queue, batch-resolve-later) — one shape was built, not generated and selected from several. Realize reads the same two hard-coded branches as already further along than a Tier 1 concept normally commits to: writing two specific, functioning resolution outcomes into JavaScript is a production-shaped decision (what happens when a claim is cleared) landing inside what the rail elsewhere calls a static, non-interactive-with-live-data screen (line 232, "no live PSA/RMM connection"). One voice calls the build under-explored on options; the other calls it over-committed on the one option it picked.

### 7. [META — Owen Means/Ends, #40] ↔ [CHTR — Owen Theory of Change, #11]

The rail's "What you nailed" list includes, as its fifth point: "Math self-corrected through the pipeline's own verification gate — the 47% rule caught a real miscount before it shipped" (lines 367-369). Means/Ends flags the conflation: the *means* being celebrated is the process (a gate exists, it caught an error); the *end* implied by putting it under "what you nailed" is that the number is now trustworthy. But the corrected number — 43% — is still 13 points past the 30% threshold the same rail names as the standard (line 329). Catching your own error is not the same claim as the evidence now being sufficient, and the bullet's placement under "nailed" invites reading it that way. Theory of Change names the missing link explicitly: the chain the rail sells a viewer is "verification gate exists → catches errors → number is trustworthy → screen is ready to be critiqued honestly." Only the second arrow (gate catches errors) has actually been demonstrated, once. The third and fourth arrows are asserted, not shown.

## Executive summary

This build is internally disciplined and externally undertested: the confirm-gate mechanism, the honesty about the 43%/25% figures, and the scope restraint (one hybrid section, not fifteen tabs) are all executed cleanly against the brief's own terms, but at least four of the seven tensions above (1, 3, 5, 7) turn on the same unresolved question from the underlying brief — Q2, operator-vs-buyer, whether reused vocabulary reads as intended to someone who has never seen it — which no amount of clean execution in HTML can answer without contact with an actual MSP. Tension 2, found only by inspecting the actual table markup, suggests the "checkable by inspection" Gate 3 criteria this build claims to satisfy (dual-surface structural check, overclaiming-language check) may not have been inspected as closely as the rail implies, since a duplicated-column redundancy this visible went unflagged by both critic passes. Read as a readiness signal: this build is ready to provoke a Tier 2 discovery conversation with a real operator, not ready to be treated as evidence that the mechanism itself is the right one — the polish is ahead of the proof, which is exactly what a Tier 1 Concept is supposed to be, provided nobody upstream forgets that on the way to the next tier.
